# system — 성능·인프라·안정성 (돌아가는 것을 빠르고 튼튼하고 싸게)

SKILL.md 의 `{{ }}` 네 칸을 이 파일로 채운다.
이 도메인의 기준점은 바깥이 아니라 **안에** 있다. 비교 대상은 남의 제품이 아니라 개선 전 우리 시스템의 실측치다.
그래서 리서치보다 **먼저 측정**하는 것이 중요하고, 이 변형은 사실상 worktree 모드를 전제한다 (최적화할 대상이 이미 저장소에 있다).

## 1. 기준점 — 현행 실측치와 목표 SLO

현행 수치가 있는지 먼저 확인한다. 없으면 프롬프트의 **첫 순차 항목이 "현행 측정"**이다. 측정 없이 최적화하면 개선을 증명할 수 없다.

수집할 것:

- 현행 실측치: p50·p95·p99 지연, 처리량, 오류율, 자원 사용량, 비용. 측정 조건까지.
- 목표 SLO: 얼마까지 가야 하는가. 없으면 체크포인트 1 에서 묻는다 — 리서치로 알 수 없다.
- 부하 프로파일: 실제 트래픽 형태(피크·분포·동시성). 합성 부하만으로는 착각한다.
- 리서치로 보완: 해당 스택의 알려진 병목 패턴, 표준 벤치마크 수치, 흔한 안티패턴.

**평균만 있는 기준점을 받지 마라.** 성패는 대부분 꼬리에서 갈린다. p99 와 최악값을 기준점에 넣는다.

이 도메인에는 리뷰에서 가져올 "실패의 정의"가 없다. 기본 정의를 쓴다: **목표 지표에 닿아도 오류율·출력 등가성·메모리·롤백 가능성 중 하나라도 base 보다 나빠지면 실패.** 저장소 고유의 것이 있으면 덧붙인다.

## 2. 체크리스트 원형 — 깨지면 안 되는 불변식

성능 목표는 종료 지표다. 체크리스트는 **빨라지는 대신 잃어서는 안 되는 것**을 지킨다. 최적화는 거의 항상 무언가를 교환한다 — 무엇을 교환하지 않을지 못 박는 자리다.

| 나쁜 항목 | 좋은 항목 |
|---|---|
| 빨라졌는가 | p99 지연이 목표 이하이면서 오류율이 개선 전 대비 증가하지 않았는가 |
| 안정적인가 | 의존 서비스 하나를 죽였을 때 전체가 아니라 해당 경로만 실패하는가 |
| 결과가 같은가 | 개선 전후 동일 입력 1만 건의 출력이 바이트 단위로 일치하는가 |
| 자원을 잘 쓰는가 | 피크 부하 30분 유지 시 메모리 사용량이 단조 증가하지 않는가 |
| 되돌릴 수 있는가 | 롤백 절차가 문서화돼 있고 실제로 실행해 성공했는가 |

그 밖의 축: 동시성 안전성, 캐시 무효화 정확성, 재시도 멱등성, 백프레셔, 관측 가능성(지표·로그), 설정 변경만으로 되돌릴 수 있는가.

## 3. 검증 증거 — 부하를 걸고 장애를 주입해서 계측한다

**필수 도구**: 부하 생성기 하나(k6·hey·wrk·ab·locust). CLI·함수 벤치면 hyperfine 또는 언어별 벤치. 공유 DB·캐시·큐를 격리해야 하면 docker. 없으면 `references/tools.md` 의 system 행으로 체크포인트 1½ 를 연다.

````
검증자는 코드를 읽고 빨라졌을 것이라고 판단하지 마라. **계측한 값만 근거로 인정한다.**

  git worktree add ../base-perf {{SHA}}
  # ../base-perf 와 현재 worktree 를 같은 부하 프로파일로 각각 측정한다. 측정 순서를 바꿔 한 번 더 돌려 순서 효과를 확인한다.
  git worktree remove ../base-perf   # 끝나면 정리

1. 동일 조건 재측정: 같은 부하·같은 하드웨어·같은 워밍업으로 p50/p95/p99/최악값을 표로. {{티어별 반복 횟수}}, 분산도 함께.
2. 등가성 확인: 개선 전후 출력이 동일한지 대량 입력으로 대조해라. 성능은 정확성을 깎아 얻을 수 있으므로 이 확인 없이는 어떤 수치도 무효다.
3. 장애 주입: 의존 서비스 지연·실패, 자원 고갈, 네트워크 단절 중 {{티어별 개수}}개를 주입하고 무너지는 방식을 관찰해라. 조용히 잘못된 결과를 내는 것이 가장 나쁘다.
4. 지속 부하: {{티어별 시간}} 유지하며 메모리·핸들 누수를 확인해라.
5. 롤백 실행: 문서만 보지 말고 실제로 되돌려서 성공하는지 확인해라.

측정 환경을 재현할 수 없으면 그 범위를 판정문에 명시하고 어떤 수치가 추정인지 구분해라.
````

## 4. 종료 지표 — 꼬리 지표 + 회귀 없음

```
체크리스트 전 항목 Yes + {{지표}}가 {{목표}} 이하/이상 + 개선 전 대비 회귀 0건 · 최대 {{M}}라운드
```

- 목표는 꼬리 지표로 쓴다. "평균 30% 개선"이 아니라 "p99 200ms 이하".
- **회귀 0건**을 반드시 넣는다. 한 지표를 올리고 다른 지표를 떨어뜨리는 것을 막는다.
- 목표에 도달했지만 교환 비용이 큰 경우(메모리 3배)를 대비해 검증자가 **교환된 것을 명시적으로 보고**하게 한다.
- 개선 여지가 없다는 결론도 정당하다. 병목이 다른 곳에 있음을 계측으로 보였다면 그것으로 종료한다.

## 5. 팬아웃·순차 후보

- 팬아웃: 프로파일링, 부하 생성기 작성, 관측 지표 정비, 문서·런북.
- 순차로 닫을 것: 병목 진단 → 변경 → 재측정. 이유: 같은 시스템 상태와 같은 측정 기준선에 쓰기를 한다.
  여러 최적화를 동시에 넣으면 무엇이 효과였는지 영원히 알 수 없다. 변경은 한 번에 하나씩, 각각 재측정.
- "측정 없이 최적화하지 마라"를 프롬프트 본문에 명시한다. 받는 모델은 추측으로 고치려 든다.
- lite 는 팬아웃 없음. "측정 → 최상위 병목 하나만 수정 → 재측정" 으로 범위를 좁힌다.

## 6. worktree 모드에서 더해지는 것 — 파일 격리보다 측정 격리

base commit 이 단순한 앵커가 아니라 **측정 대상 그 자체**다. 기억에 남은 옛 수치와 비교하지 않고 같은 하드웨어에서 나란히 잰다 (3절 블록).

같은 머신에서 부모 저장소의 개발 서버가 돌면 CPU·메모리·디스크 경합이 곧 측정 오차다. 금지 목록에 반드시 넣는다:

- 측정 중 같은 머신에서 다른 빌드·테스트·개발 서버를 돌리지 않는다 (측정 전 확인하고 보고)
- 부모 저장소와 공유하는 DB·캐시·큐에 부하를 걸지 않는다. 격리된 인스턴스를 띄운다
- 포트는 worktree 전용으로 배정한다

회귀 항목 +1: **벤치마크 하니스·부하 생성기·측정 스크립트 자체가 base commit 대비 변경되지 않았는가** (변경했다면 base 도 새 하니스로 다시 측정했는가).
하니스를 고쳐야 한다면 그 변경을 먼저 병합하고 최적화를 시작한다. 한 브랜치에서 둘 다 하지 않는다.
하니스가 아예 없는 저장소면 **예외로 한 브랜치에서 한다**: 첫 순차 항목이 "하니스 작성 → 라운드 0 커밋"이고, 그 커밋 SHA 가 하니스 불변의 기준이다.
base 측정은 base worktree 에 그 하니스를 복사해서 한다 (`cp -r bench ../base-perf/`) — 하니스 파일은 회귀 통의 "변경 범위" 검사에서 제외한다고 프롬프트에 적는다.
