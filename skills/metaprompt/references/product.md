# product — 사람이 쓸 물건 (UI·앱·웹·대시보드·게임) · 증거는 렌더

"예쁨"은 점수가 흔들린다. 그래서 **수치로 바꿀 수 있는 지각 속성**만 체크리스트에 올리고, 결과물을 실제로 렌더해서 판정한다.

## 1. 기준점 (creative) — 리서치에서 수집할 것

- 후보 제품 3개 (lite 2개) 와 각각의 구체적 사실 — 화면 구성, 정보 밀도, 색 사용, 핵심 인터랙션, 상징적 특징
- 사용자·리뷰어가 좋다고 말하는 **이유**, 그리고 불만 (앞서기 항목의 재료)
- 실패의 정의 — 비교 리뷰의 "차별화 실패" 표현 그대로. 없으면 이 주제의 기본 위젯·템플릿을 실명으로 들어 한 문장.

precise × product (레이아웃 버그·접근성 수정 등) 는 기준점이 base commit 화면이다. 회귀 테스트 대신 **base 캡처와의 픽셀 대조 스크립트**가 빨강이 될 수 있다.

## 2. 체크리스트 원형 — 지각 속성의 수치

| 나쁜 항목 | 좋은 항목 |
|---|---|
| 애니메이션이 자연스러운가 | 전환이 200ms 이하이고 끊김이 없는가 |
| 색이 예쁜가 | 다크모드에서 모든 텍스트 대비가 4.5:1 이상인가 |
| 반응이 빠른가 | 필터 토글이 전체 리마운트 없이 200ms 이내에 반영되는가 |
| 구분이 잘 되는가 | 그레이스케일로 변환해도 종류가 구분되는가 |

자주 쓰는 축: 대비비, 응답 시간, 리마운트 여부, 상태 보존, 색맹 대응, 키보드 접근성, 좁은 폭. **정보 밀도**가 대부분의 제품 비교에서 승부처다.
함정: 항목 하나가 기준점의 미학과 충돌하면 도달 가능한 최고점이 10~12점 깎였다 (실측). 동시 만족 점검에서 본다.

## 3. 검증 증거 — 실제로 렌더해서 픽셀을 본다

**필수 도구**: 헤드리스 브라우저 하나 — 환경 JSON 의 `browser`, 또는 `python_packages.playwright` + `playwright_browsers` 에 chromium.
코드만 읽은 채점(77점)과 렌더를 준 채점(75점)이 달랐고, 렌더에서만 보인 지적이 셋 나왔다 (실측). 프롬프트의 검증 섹션에 넣는다:

````
검증자는 결과물을 **실제로 렌더링해서 픽셀을 보고** 판정해라. CSS 를 읽고 화면을 상상하지 마라.

  google-chrome --headless=new --disable-gpu --no-sandbox --hide-scrollbars \
    --virtual-time-budget=5000 --window-size=1440,987 --screenshot=OUT.png "file:///절대경로"

- `--window-size` 높이에서 약 87px 뺀 값이 실제 뷰포트다 (1440x987 → 1440x900).
- 다른 상태(다크·좁은 폭·다른 뷰)는 원본 **사본**에 스크립트를 주입해 만든 뒤 캡처한다. 원본은 수정하지 마라.
- 헤드리스 창은 500px 보다 좁아지지 않는다. 390 폭은 사본을 `<iframe width=390>` 에 넣어 잰다. "스크롤 없이 들어오는가"는 PNG 가 아니라 스크립트로 `innerHeight` 와 요소 위치를 비교한다.
- 대비비 같은 수치는 스크립트로 계산해 값을 보고한다. 렌더 도구가 없으면 판정문에 명시한다.
````

| 티어 | 캡처 세트 |
|---|---|
| lite | 2장 — 기본 화면 + 체크리스트가 요구하는 상태 1장. 대비는 텍스트 색 3쌍 |
| standard | 4장 — 라이트/다크, 대체 뷰, 좁은 폭. 대비는 전체 텍스트 색 |
| max | 4장 + 2x DPI + hover·포커스·빈 상태. 대비는 색 × 합성 배경 전수 |

캡처 한 장은 체크리스트 항목 최소 하나의 근거여야 한다. 브라우저가 아닌 산출물(CLI·TUI)은 그에 맞게 구동해서 관찰한다.

## 4. 종료 지표 (creative)

| 티어 | 문장 |
|---|---|
| lite | 체크리스트 전 항목 Yes (점수 없음) |
| standard | 체크리스트 전 항목 Yes + 블라인드 비교에서 {{기준점}} 대비 75점 이상 |
| max | 체크리스트 전 항목 Yes + 블라인드 비교에서 {{기준점}} 대비 80점 이상 |

80 이 현실적 상한 근처다 (실측 궤적 63 → 74 → 75 → 79 → 80). standard+ 는 사용성 과업 한 줄을 주고 **조작 횟수를 세게** 한다.

## 5. 팬아웃·순차

- 팬아웃 후보: 컬러 시스템, 아이콘, 타이포·스페이싱, 빈 상태·로딩 화면. lite 는 팬아웃 없이 이것들을 빌더 작업 순서 앞쪽에.
- 순차: 렌더링·좌표계·상태 전이·레이아웃·필터 반영 경로. 이유: 같은 데이터 구조와 좌표계에 쓴다 — 실측 최악의 결함 셋이 전부 이 이음매에서 나왔다.

## 6. worktree 에서 더해지는 것

- 외부 기준점의 미학 vs 기존 디자인 시스템: 체크포인트에서 묻는다. "기존 따름"이면 외부 기준점은 레이아웃·밀도·인터랙션에만.
- 회귀 항목 +1: **변경 범위 밖 화면의 캡처가 base commit 과 동일한가.** base 는 `git worktree add ../base-snapshot <SHA>` 로 같은 조건에서 캡처한다.
