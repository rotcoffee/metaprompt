# product — 사람이 쓸 물건 (UI·앱·웹·대시보드·게임)

SKILL.md 의 `{{ }}` 네 칸(기준점 종류 · 체크리스트 원형 · 증거 획득 · 종료 지표)을 이 파일로 채운다.
이 도메인은 "예쁨"이 주관적이라 점수가 흔들린다. 그래서 **수치로 바꿀 수 있는 지각 속성**만 체크리스트에 올린다.

## 1. 기준점 — 실명 제품

"업계 최고"·"요즘 앱처럼"은 기준점이 아니다. 제품 이름이어야 검증자가 그 제품의 공개 자료를 찾아 결과물과 나란히 놓을 수 있다.

리서치에서 수집할 것:

- 후보 제품 3개 (lite 는 2개) 와 각각의 구체적 사실 — 화면 구성, 정보 밀도, 색 사용 방식, 핵심 인터랙션, 상징적 특징
- 사용자·리뷰어가 좋다고 말하는 **이유**
- **실패의 정의** — 비교 리뷰에서 "차별화 실패"로 묶인 표현 그대로. 실측(캘린더 과제)에서는 "폰트만 다른 기본 캘린더"였고,
  이 문장이 검증자 판정문에 그대로 되돌아왔다. 검증자가 매 라운드 이걸 기준으로 묻게 된다.
  **이 예시 문장을 다른 주제에 복사하지 마라.** 리뷰 표현을 못 찾았으면(lite 에서 흔하다) 그 주제에서 "평범함"이 무엇인지 한 문장으로 직접 정의한다 —
  "기본 위젯·템플릿과 구분되지 않으면 실패" 꼴로, 그 주제의 기본 위젯이 무엇인지 실명으로.

## 2. 체크리스트 원형 — 지각 속성의 수치

| 나쁜 항목 | 좋은 항목 |
|---|---|
| 애니메이션이 자연스러운가 | 전환이 200ms 이하이고 끊김이 없는가 |
| 색이 예쁜가 | 다크모드에서 모든 텍스트 대비가 4.5:1 이상인가 |
| 정보가 잘 보이는가 | 지난 항목이 흐리되 대비 3:1 이상을 유지하는가 |
| 반응이 빠른가 | 필터 토글이 전체 리마운트 없이 200ms 이내에 반영되는가 |
| 구분이 잘 되는가 | 그레이스케일로 변환해도 종류가 구분되는가 |

자주 쓰는 축: 대비비, 응답 시간, 리마운트 여부, 그레이스케일 판별, 상태 보존(뷰 전환 시 기준 위치 유지), 색맹 대응, 키보드 접근성, 축소 동작.
**정보 밀도 조절**이 대부분의 제품 비교에서 승부처다. 기준점 상세에 밀도 관련 사실을 꼭 넣는다.

함정: 항목 하나가 기준점의 미학과 충돌하면 도달 가능한 최고점이 깎인다. 실측에서 "아이콘 상시 노출" 한 항목이
기준점의 미니멀리즘과 정면 충돌해 상한을 10~12점 낮췄다. 체크포인트 3 전에 **동시 만족 가능성**을 반드시 본다.

## 3. 검증 증거 — 실제로 렌더해서 픽셀을 본다

이 도메인에서 가장 중요한 칸이다. 비워 두면 검증자는 CSS 를 읽고 화면을 상상해서 채점한다.
실측에서 같은 파일이 코드만 읽었을 때 77점, 실제 렌더링을 준 뒤 75점이었고 코드에서는 보이지 않던 지적 셋이 새로 나왔다.

프롬프트의 검증 섹션에 아래를 넣는다. 캡처 장수만 티어로 조절한다.

````
검증자는 결과물을 **실제로 렌더링해서 픽셀을 보고** 판정해라. CSS를 읽고 화면을 재구성하지 마라.

  google-chrome --headless=new --disable-gpu --no-sandbox --hide-scrollbars \
    --virtual-time-budget=5000 --window-size=1440,987 --screenshot=OUT.png "file:///절대경로"

- `--window-size` 높이에서 약 87px 뺀 값이 실제 뷰포트다 (1440x987 → 1440x900). 모르면 캡처 하단 여백을 레이아웃 버그로 오인한다.
- 다른 상태(다크·다른 뷰)는 **원본 사본**의 `</body>` 앞에 스크립트를 주입해 만든 뒤 캡처한다. 원본은 수정하지 마라.
- 캡처 세트: {{티어별 — 아래 표}}
- 대비비·광도 같은 수치는 추정하지 말고 스크립트로 계산해서 값을 보고해라.
- 렌더링 도구가 없으면 그 사실을 판정문에 명시하고 진행해라. 조용히 건너뛰지 마라.
````

| 티어 | 캡처 세트 |
|---|---|
| lite | 2장 — 기본 화면 라이트 + 체크리스트가 요구하는 상태 1장(좁은 폭·다크·대체 뷰 중 하나). 대비는 텍스트 색 3쌍만 계산 |
| standard | 4장 — 라이트/다크, 대체 뷰, 좁은 폭. 대비는 전체 텍스트 색 계산 |
| max | 4장 + 2x DPI + 상호작용 상태(hover·포커스·빈 상태). 대비는 색 × 합성 배경 전수 계산 |

캡처 한 장은 체크리스트 항목 최소 하나의 근거여야 한다. 대응 항목이 없는 캡처는 빼고, 근거 없는 항목은 캡처를 더한다 — 둘의 짝이 맞아야 검증자가 상상으로 채우지 않는다.
브라우저가 아닌 산출물(CLI·데스크톱)이면 그에 맞는 관찰 방법으로 바꾼다. 핵심은 **결과물을 실제로 구동해서 관찰한다**는 것이다.
`detect_env.py` 의 `browser` 가 null 이면 프롬프트에 "브라우저 설치 또는 대체 관찰 방법"을 첫 순차 항목으로 넣는다.

## 4. 종료 지표

| 티어 | 문장 |
|---|---|
| lite | 체크리스트 전 항목 Yes (점수 없음) |
| standard | 체크리스트 전 항목 Yes + 블라인드 비교에서 {{기준점}} 대비 75점 이상 |
| max | 체크리스트 전 항목 Yes + 블라인드 비교에서 {{기준점}} 대비 80점 이상 |

- 80 이 현실적 상한 근처다 (실측 궤적 63 → 74 → 75 → 79 → 80). 90 을 걸려면 체크리스트가 그걸 허용하는지 먼저 본다.
- standard 이상은 검증자에게 **디자인 평가와 사용성 테스트를 100점 만점으로** 채점하게 하고,
  사용성 시나리오를 실제 과업 한 줄로 준다 ("다음 주 특정 종류의 항목만 찾기"). **몇 번의 조작으로 끝나는지 세게** 한다.
- 점수는 입력 조건에 따라 흔들린다. 항목별 판정과 근거 수치가 1차 결론임을 명시한다.

## 5. 팬아웃·순차 후보

- 팬아웃: 컬러 시스템, 아이콘 세트, 타이포·스페이싱, 빈 상태·로딩·설정 화면. (K 개 이하로 고른다)
- 순차로 닫을 것: 렌더링·좌표계·상태 전이·레이아웃 배치·필터 반영 경로.
  이유: 같은 데이터 구조와 같은 좌표계에 쓰기를 한다. 실측에서 가장 심각한 결함 셋이 전부 이 이음매에서 나왔다.
- lite 는 팬아웃 없음. 팬아웃 후보를 빌더의 작업 순서 앞쪽에 놓는다 (팔레트·타이포를 먼저 정하고 코어를 짠다).

## 6. worktree 모드에서 더해지는 것

결과물이 홀로 평가받지 않고 **이미 있는 화면 옆에 놓인다.** 그래서 긴장이 하나 생긴다.

- 외부 기준점의 미학 vs 저장소의 기존 디자인 시스템. 그대로 두면 받는 모델이 매 라운드 둘 사이를 오간다.
  체크포인트 1 에서 묻는다: "기존 토큰 따름"이면 외부 기준점은 레이아웃·밀도·인터랙션에만 적용,
  "새 방향"이면 외부 기준점이 이기되 공용 헤더·네비·모달 같은 접점을 순차 항목으로 닫는다.
- 저장소 조사에서 추가 수집: 디자인 토큰·테마 변수 위치와 값, 재사용 컴포넌트 목록, 이 화면의 진입·이탈 경로.
- 회귀 항목 +1: **변경 범위 밖 화면의 스크린샷이 base commit 과 동일한가** (달라졌다면 이유가 설명되는가)
- 증거 획득에 before/after 대조를 더한다:

````
base commit 화면을 별도 worktree 에 체크아웃해 같은 조건으로 캡처하고 현재와 나란히 비교해라.

  git worktree add ../base-snapshot {{SHA}}
  # 양쪽을 같은 --window-size 로 캡처해 비교. 끝나면 git worktree remove ../base-snapshot

- 변경 범위 밖 화면은 동일해야 한다. 달라졌으면 회귀다.
- 변경 범위 안은 "달라졌다"가 아니라 "나아졌다"를 근거로 보여라.
````
