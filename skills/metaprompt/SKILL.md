# metaprompt

주제 한 줄 → **다른 세션에서 실행할 프롬프트 파일 하나.** 프로그램을 만들지 않고, 만든 프롬프트를 실행하지도 않는다.

철학은 oneshot 을 잇는다: 기준점 고정 · 리서치 선행 · 팬아웃/순차 분리 · 생성자/검증자 분리 · Yes/No 체크리스트 · 숫자 종료 조건.
"예쁘게 만들어 줘"와 "○○ 대비 아래 7개 항목 전부 Yes 가 될 때까지"의 차이가 결과물의 차이다. 사람은 반드시 빠뜨리고, 이 스킬이 대신 채운다.

여기서 더한 것 넷: **티어**로 품질↔토큰을 고른다 · 결정 지점마다 **사용자 확인**을 받는다 · 리서치와 환경 조사를 **서브에이전트·스크립트에 위임**해 이 컨텍스트를 아낀다 · 실행 시 컨텍스트 절약 규약(30줄 보고, 판정문 파일화)을 프롬프트에 박는다.

입력: `$ARGUMENTS`

## 환경 (스킬 로드 시 자동 수집)

```!
python3 ${CLAUDE_SKILL_DIR}/scripts/detect_env.py --skill-dir ${CLAUDE_SKILL_DIR}
```

위 JSON 의 `skill_dir` 이 이 스킬의 디렉터리다 — 아래에서 `<skill_dir>` 로 쓴다. 위 블록이 JSON 이 아니라 "run this first" 지시로 보이면 그 커맨드를 그대로 실행한다. 그것도 안 되면 `find ~/.claude -path '*metaprompt/scripts/detect_env.py' | head -1` 로 스크립트를 찾아 실행한다. `mode` 는 `--mode` 가 오면 덮어쓴다.

**`--check` 만 왔으면** 여기서 끝낸다: 환경 JSON 을 그대로 보여주고 `python3 <skill_dir>/scripts/check_prompt.py --self-test` 의 마지막 줄을 붙여 설치 상태를 한 줄로 보고한다. 프롬프트를 만들지 않는다.

## 파일 지도 — 필요할 때만 읽는다

| 파일 | 언제 |
|---|---|
| `references/product.md` · `research.md` · `system.md` | 체크포인트 1 이후, **판정된 도메인 하나만** |
| `references/worktree.md` | mode 가 worktree 일 때만 |
| `references/template.md` | 5단계 조립 직전 |
| `scripts/check_prompt.py` | 6단계 자가점검 |
| `fixtures/*.md` | 조립 형식이 헷갈릴 때 하나만 (선택) |

셋을 미리 읽지 않는다. 필요한 것만 필요한 때 읽는 것이 이 스킬이 oneshot 보다 가벼운 첫째 이유다.

## 티어 — 품질과 토큰의 교환

| | **lite** | **standard** (기본) | **max** |
|---|---|---|---|
| 생성 시 리서치 | 서브에이전트 없음. 모델 지식 + 검색 ≤1회 | 서브에이전트 1 (sonnet) | 서브에이전트 3 병렬 |
| 체크포인트 | 2회 (1·3 — 기준점은 1 의 네 번째 문항) | 3회 | 3회 |
| 체크리스트 | 4~5 항목 | 6~7 | 7~8 |
| 프롬프트 예산 | 팬아웃 K=0 · 라운드 M=2 · 정체 S=2 · 증거 최소 세트 | K≤3 · M=3 · S=2 · 표준 세트 | K≤5 · M=5 · S=3 · 전체 세트 + 블라인드 비교 |
| 실행 방법 | `claude` 새 세션에 붙여넣기 | `/loop` + 붙여넣기 | `/loop ultracode` + 붙여넣기 |
| 실행 비용 (추정) | 서브에이전트 2~4 · 30분~1시간 · oneshot 대비 ~1/10 | 6~10 · 1~3시간 · ~1/3 | 15~20 · 3~7시간 · oneshot 실측과 같음 |
| 언제 | 내부용 초안, "일단 기준 있는 버전" | 남에게 보여줄 것 | 경쟁 제품 옆에 놓일 것, 논문 재현 |

lite 가 깎는 것은 **리서치 깊이·팬아웃·라운드·증거 범위**다. 기준점 고정, 검증자 분리, Yes/No 체크리스트, 정체 감지는 어느 티어에서도 빼지 않는다 — 그것을 빼면 그냥 평범한 프롬프트다.
티어 승격은 싸다: 프롬프트 헤더의 `regenerate:` 줄을 `--from` 으로 다시 부르면 리서치를 재사용한다.

티어 추천 규칙: "빠르게·초안·내부용·일단" → lite. "논문·출시·경쟁·포트폴리오·SOTA" → max. 그 외 standard.

## 절차

### 0. 파싱과 판정

1. 인자에서 주제와 플래그를 읽는다. `--from` 이 있으면 그 파일의 헤더·기준점 상세·체크리스트를 가져오고 2단계(리서치)를 건너뛴다.
2. 환경 JSON 에서 mode · 저장소 사실 · 브라우저 유무를 읽는다. worktree 인데 `dirty_count > 0` 이면 안내문에 "먼저 정리"를 넣을 것을 기억한다.
3. 도메인을 판정한다. 신호 → 판정:
   UI·화면·앱·웹·대시보드·게임·사용자가 쓴다 → `product` / 논문·재현·벤치마크·가설·ablation·"정말 나아졌는지" → `research` /
   성능·지연·처리량·최적화·인프라·안정성·비용 절감 → `system`. 경계: "만들어서 쓴다" 는 product·system, "나아졌음을 보인다" 는 research.
4. 티어를 추천 규칙으로 정한다. `--tier` · `--profile` · `--mode` 가 있으면 판정 대신 그것을 쓴다.
5. 도메인 판정이 확실하면 (플래그로 왔거나 신호가 한쪽뿐이면) 지금 도메인 레퍼런스를 읽는다 — lite 는 체크포인트 1 에서 기준점 후보를 내야 하므로 반드시 읽는다. 애매하면 체크포인트 1 의 답을 받은 뒤 읽는다.

도메인과 모드는 독립이다. 저장소 안에서 UI 를 만들 수도, 빈 디렉터리에서 연구 코드를 짤 수도 있다.

### 1. 체크포인트 1 — 판정 확인 (AskUserQuestion 1회)

`--yes` 면 건너뛰고 판정을 한 줄로 통보한 뒤 진행한다. `--from` 이면 티어·진행 방식만 묻는다 (도메인·모드·기준점은 헤더에서 온다). 아니면 **한 번의 호출**에 아래 문항을 담는다. 추천 옵션을 첫 번째에 두고 라벨 끝에 `(Recommended)` 를 붙인다.

| 문항 | 옵션 | 설명에 넣을 것 |
|---|---|---|
| 도메인 | product / research / system | 각 도메인의 기준점 종류와 검증 방식 한 줄 |
| 티어 | lite / standard / max | 티어 표의 **실행 비용 추정과 라운드·팬아웃 수**. 사용자가 여기서 트레이드오프를 고른다 |
| 진행 방식 | 체크포인트마다 확인 / 이후는 추천값으로 자동 | 후자를 고르면 체크포인트 2·3 을 건너뛴다 |
| 네 번째 (필요할 때만) | 상황별 | 아래 중 하나 |

네 번째 문항은 리서치로 알 수 없고 **사용자만 아는 것**에 쓴다. 우선순위:
system 인데 목표 SLO 가 없다 → 목표치 / worktree 인데 테스트 커맨드를 못 찾았다 → 커맨드 / worktree × product → 기존 디자인 시스템을 따를지 새 방향인지 /
lite → 기준점 후보 2개를 모델 지식으로 제시하고 고르게 한다 (이것이 lite 의 체크포인트 2 를 대신한다) / 그 외 → "이미 실패한 접근·제약·예산이 있는가" (없음 / 있음은 Other 로 입력).

문항은 4개를 넘기지 않고, 이 체크포인트 밖에서 추가로 묻지 않는다. 인터뷰 스킬이 아니다.
답을 받으면 아직 안 읽은 도메인 레퍼런스를 읽는다 (worktree 면 `worktree.md` 도).

### 2. 리서치 — 이 컨텍스트에서 하지 않는다

검색 결과 본문은 크고 대부분 버려진다. 서브에이전트가 소비하고 **압축된 사실만** 돌려받는다. Agent 도구를 쓰고, 여러 개면 한 메시지에서 동시에 띄운다.

| 티어 | 에이전트 | 모델 |
|---|---|---|
| lite | 없음. 체크포인트 1 에서 고른 후보를 검색 최대 1회로 보강. 확인 못 한 사실은 `(출처 미확인)` | — |
| standard | 기준점 조사 1 (general-purpose) | sonnet |
| max | 기준점 후보 · 실패의 정의와 비교 리뷰 · 도메인 함정, 3개 병렬 | 후보 조사만 세션 모델, 나머지 sonnet |
| worktree (standard+) | 저장소 조사 1 (Explore) 추가 — `worktree.md` 의 항목, 20줄 이내·줄당 120자 이내. 외부 조사와 **동시에** 띄우되 조립에서는 저장소 사실이 우선 | sonnet |

리서치 에이전트 프롬프트에 넣을 것: 주제 · 도메인 · 도메인 레퍼런스 1절 "리서치에서 수집할 것" 을 그대로 · `--benchmark` 가 있으면 그것을 후보 1로 고정 · 아래 반환 형식.

```
반환은 40줄 이내, 이 형식만. 검색 결과 본문·인용문을 붙이지 마라.
후보 1: <기준점 후보> — 사실 (1) … (2) … (3) … [수치 우선] — 출처: <URL>
후보 2: … / 후보 3: …
실패의 정의: "<리뷰 표현 그대로, 없으면 '없음'>" — 출처
함정: (1) … (2) …
```

"후보"의 종류는 도메인 레퍼런스 1절이 정한다 — product: 실명 제품 / research: 보고 수치와 그 조건 / system: 같은 스택의 공개 벤치마크 수치와 알려진 병목 패턴 (현행 실측치는 저장소 조사가 가져온다).

### 3. 체크포인트 2 — 기준점 선택 (standard·max)

후보 2~3개를 옵션으로, 설명에 핵심 사실 두 개와 실패의 정의를 넣는다. 추천을 첫 번째에. 사용자는 Other 로 직접 지정할 수 있다.
"자동 진행"을 골랐거나 `--yes` 면 추천 후보로 진행하고 한 줄로 통보한다.

### 4. 초안 — 체크리스트·종료 조건·분배, 그리고 체크포인트 3

도메인 레퍼런스의 2·4·5절로 아래를 만든다.

- 체크리스트 (티어 항목 수). 리서치 사실을 그대로 Yes/No 항목으로 바꾸는 것이 가장 좋다. "좋은가"로 끝나는 항목은 전부 다시 쓴다.
- worktree 면 회귀 통 (기본 3 + 도메인 1). 도메인 통과 **따로** 센다.
- 종료 지표 문장과 라운드 상한 M, 정체 판정 S (위 티어 표 · `--rounds` 가 오면 M 만 그것).
- 팬아웃 항목(K 개 이하)과 순차 코어, 순차인 **이유** — 같은 상태·파일·순서에 쓰기를 하면 순차. 애매하면 순차로 닫는다.
- **동시 만족 가능성 점검**: 항목끼리, 항목과 기준점의 미학, 항목과 회귀 통이 상충하는가. 실측에서 항목 하나가 도달 가능한 최고점을 10~12점 깎았다.
  상충이 보이면 고치거나, 상충을 프롬프트에 명시하고 종료 점수를 그만큼 낮춘다.

체크포인트 3 (`--yes` 또는 "자동 진행"이면 건너뛰고 초안 요약을 서너 줄로 통보만 한다. 상충은 기본값 **항목 수정**으로 해소한다):
위 초안을 메시지에 **짧게** 보여준다 (체크리스트 번호 목록, 회귀 통, 종료 문장, 팬아웃/순차 한 줄, 상충 점검 결과).
그다음 AskUserQuestion 1회 — "체크리스트·종료 조건": `그대로 진행 (Recommended)` / `수정 (Other 에 번호와 내용)`.
상충이 발견됐으면 두 번째 문항으로 해소 방법을 고르게 한다: `항목 수정 (Recommended)` / `상충 명시 후 진행` / 점수가 있는 티어(standard·max)만 `종료 점수 하향`.
수정 요청이 오면 반영하고 바뀐 항목만 한 줄로 확인한다. 다시 묻지 않는다.

### 5. 조립

`references/template.md` 를 읽고 그 규칙대로 채운다. 섹션 순서 고정, `{{ }}` 전부 채움, 조건 블록은 티어·모드에 맞는 것만.
증거 획득 블록은 도메인 레퍼런스 3절을 티어 표에 맞게 조정해 넣는다. 실제 커맨드가 들어가야 한다 — 비워 두면 검증자가 상상으로 채점한다.
헤더 주석의 `regenerate:` 줄에 재생성 커맨드를 정확히 적는다.

### 6. 자가점검 · 저장 · 안내

저장 경로: `--out` 또는 `./prompts/metaprompt-<슬러그>.md`. `--from` 원본과 같은 경로인데 티어가 바뀌었으면 `-<새 티어>` 접미사를 붙여 새 파일로 저장한다 (이전 티어의 프롬프트를 지우지 않는다). worktree 모드에서는 이 기본 경로가 저장소 안이다 — 프롬프트 파일이 커밋에 섞이지 않게 `prompts/` 를 `.gitignore` 에 두거나 `--out` 으로 밖에 저장하라고 안내문에 한 줄 넣는다. 저장 후 검사한다.

```bash
python3 <skill_dir>/scripts/check_prompt.py <저장 경로>
```

FAIL 이 있으면 고쳐서 다시 검사한다 (최대 2회). 그래도 남으면 **어떤 항목이 왜 남았는지 사용자에게 알린다.** 조용히 저장하고 끝내지 않는다.

마지막 메시지는 아래 한 화면. 아래는 틀이고, 실제 출력에는 **판정된 모드와 티어의 줄만** 남긴다 — greenfield 안내를 기존 저장소에서 돌리면 파일을 덮어쓰며 사고가 난다.

```
저장: <경로>
도메인 <d> · 티어 <t> · 모드 <m> · 기준점 <b> · 라운드 상한 <M> · 팬아웃 <K>
예상 비용: <티어 표의 추정치>

실행 (새 세션):
  greenfield → mkdir -p <디렉터리> && cd <디렉터리> && git init && claude
  worktree   → [dirty 면: 먼저 정리] git worktree add ../<repo>-metaprompt-<슬러그> -b metaprompt/<슬러그> && cd ../<repo>-metaprompt-<슬러그> && claude

  프롬프트 창에:
  lite     → <파일 내용 붙여넣기>            (라운드는 프롬프트 안에서 돈다. /loop 불필요)
  standard → /loop                            그다음 줄에 붙여넣기
  max      → /loop ultracode                  그다음 줄에 붙여넣기

worktree 완료 후 (사람이 판정문을 읽고): git -C <저장소> merge --no-ff metaprompt/<슬러그> && git -C <저장소> worktree remove ../<repo>-metaprompt-<슬러그>
티어 올리기: 헤더의 regenerate 줄 (--from 으로 리서치 재사용)
```

## 절대 규칙

1. **기준점 없이 프롬프트를 뱉지 않는다.** "좋게"·"고품질"은 목표가 아니다. lite 라도 실명·수치다. 리서치로도 없으면 체크포인트에서 묻는다.
2. **리서치 사실 3개 이상**이 프롬프트에 들어간다. lite 는 `(출처 미확인)` 표시를 달고 넣는다. "○○처럼"만 쓰면 받는 모델이 상상으로 채운다.
3. **공유 상태를 만지는 작업은 팬아웃하지 않는다.** 서로 호출하지 않는다고 독립이 아니다. 같은 상태를 만지면 결합돼 있고 이음매에서 터진다.
4. **생성자와 검증자를 분리하고, 종료 조건은 검증자가 쥔다.** 검증자가 무엇을 보고 판정하는지 커맨드까지 지정한다.
5. **모드를 먼저 판정한다.** 기준점이 둘(외부 + base commit)인지 하나인지가 격리·회귀·종료의 의미를 바꾼다.
6. **체크포인트 밖에서 묻지 않는다.** 체크포인트는 최대 3회, 각 AskUserQuestion 1회. 질문이 늘면 토큰과 사용자 시간이 같이 샌다.
7. **프롬프트를 직접 실행하지 않는다.** 산출물은 텍스트 파일까지다.

## 하지 말 것

- 레퍼런스 셋을 미리 다 읽기 — 필요한 하나만
- 리서치를 이 컨텍스트에서 직접 하기 (lite 의 검색 1회 제외) — 검색 본문이 컨텍스트를 태운다
- 체크리스트에 "잘 동작하는가"·"보기 좋은가" 넣기
- lite 라고 검증자 분리·정체 감지·수용된 제약을 빼기 — 티어가 깎는 것은 깊이지 구조가 아니다
- 자가점검 FAIL 을 숨기고 저장하기
- 모드에 맞지 않는 실행 안내를 내보내기
